# CODE/ Sub-milestone 1b — Port Log (COMPLETE)

Parent plan: [../plans_wip/modernization_cmake_vcpkg.md](../plans_wip/modernization_cmake_vcpkg.md). **`CODE/` now builds with 0 errors** (`redalert_code.lib` produced, linking against `win32lib`) — verified via a from-scratch clean `cmake --build`. Started at ~20,800 errors on the first real build attempt against the authoritative 242-file source list (see below).

## How to reproduce
```
cmake --preset Main
cmake --build build/Main --config Release --target redalert_code
```
`CODE/CMakeLists.txt`'s source list is **not a glob** — it's the exact Win32 (`ra95.exe`) object list transcribed from Westwood's own `CODE/MAKEFILE` (`OBJECTS`/`LIBFILES`/`TECHFILES` macros plus the `!ifdef WIN32` extras), mapped to real filenames. `.ASM` files are deferred to Phase 2 (UASM), same policy as 1a.

## Tooling: clang-cl as a second opinion
A large fraction of this milestone's diagnosis used a **second, independent compiler** (LLVM/clang-cl 22.1.6, already installed at `C:\Program Files\LLVM`) alongside MSVC, via a separate CMake configuration (`build/Analysis`, Ninja generator, `clang-cl` as `CMAKE_CXX_COMPILER`, same vcpkg toolchain). Reasons this was worth the setup cost:
- `clang-tidy --checks='-*,misc-include-cleaner'` gives a precise, per-symbol "no header providing X is directly included" report — far faster than manually tracing MSVC's often-cascading, misleadingly-located errors back to a missing include.
- `-ferror-limit=0` plus clang's single-file diagnostics avoid the parallel-build log interleaving that misattributed errors to the wrong file during 1a.
- A full-codebase `-fsyntax-only` sweep script (243 files) gave a fast per-file pass/fail signal to prioritize which files had the most (or most-shared) problems.
Both compilers were needed: several bugs (notably the `TriggerTypeClass` issue below) are MSVC-2026-preview-specific and invisible to clang; most others were genuine and clang found them faster.

## Root-cause fix #1: `CODE/` listed before `WIN32LIB/INCLUDE` in the include path
Seven filenames exist in **both** directories (`AUDIO.H`, `DEFINES.H`, `EXTERNS.H`, `FILEPCX.H`, `KEYBOARD.H`, `MOUSE.H`, `RAWFILE.H`). `CODE/CMakeLists.txt` listed `CODE/` first in `target_include_directories`, so every **angle-bracket** `#include <x.h>` for one of those seven names silently resolved to `CODE/`'s high-level version instead of `WIN32LIB/INCLUDE`'s low-level one (angle-bracket lookup walks `-I` paths in listed order and does not special-case "the including file's own directory" the way quote-includes do — those were never affected). Found by tracing why `JSHELL.H`'s `#include <mouse.h>` couldn't see `Get_Mouse_X()`/`WWMouseClass`. **Fixed** by reordering `WIN32LIB/INCLUDE` before `CODE/` in `CODE/CMakeLists.txt` — matching the original Watcom `MAKEFILE`, whose `CC_CFG` listed `$(WWFLAT)\INCLUDE` explicitly rather than relying on directory order. This one fix dropped the error count by roughly 14,000 and, as a side effect, also fixed a second latent instance of the same bug inside `WIN32LIB`'s own `wwlib32.h`.

## Root-cause fix #2: `FUNCTION.H` circular self-inclusion
`ABSTRACT.H` and `GSCREEN.H` had each picked up `#include "function.h"` (apparently as an attempted fix for missing types) despite `FUNCTION.H` itself including both of them, directly or transitively, as part of its ~250-header "master include" list. This created re-entrant chains like `map.h → gscreen.h → function.h → ... → display.h → map.h(guarded, no-op) → ... ` where `DisplayClass`'s own `#include "map.h"` became a silent no-op because the OUTER `map.h` entry hadn't finished defining `MapClass` yet — leaving `DisplayClass : public MapClass` looking at an incomplete base and producing "expected class name" / "incomplete type" errors that appeared to implicate completely unrelated files. **Fixed** by removing the `function.h` include from both files and replacing it with the specific direct dependencies each one actually needs (confirmed via clang's exact "no header providing X" diagnostics) — `defines.h` for `GSCREEN.H`'s `TheaterType`; `defines.h` + a forward-declared `MonoClass`/`Coord_Cell` prototype for `ABSTRACT.H`. This single fix cleared the *entire* `map.h` → `display.h` → `radar.h` → `power.h` → `sidebar.h` → `tab.h` → `team.h` → `house.h` → `bullet.h` → `terrain.h` → `target.h` dependency chain at once (confirmed by compiling `map.h` standalone before/after: many dozens of errors → zero).

## Root-cause fix #3: missing `WOLAPI_INTEGRATION`/`WINSOCK_IPX`/`ENGLISH=1` compile definitions
The original `MAKEFILE`'s `CC_CFG` passed `/DWOLAPI_INTEGRATION /DWINSOCK_IPX /D$(LANGUAGE)=1` for the Win32 build; our CMake target never carried these forward. The consequence was silent, not a compile error: e.g. `TOOLTIP.H`'s *entire* body — including the `class ToolTipClass` declaration — is wrapped in `#ifdef WOLAPI_INTEGRATION`, so without the define the header preprocessed to nothing and `TOOLTIP.CPP`'s own out-of-line method definitions had no class to belong to (`"ToolTipClass": no class or namespace`). Found by preprocessing `TOOLTIP.CPP` with `/P` and noticing `ToolTip.h`'s file-entry marker was immediately followed by nothing. **Fixed** by adding `target_compile_definitions(redalert_code PRIVATE WOLAPI_INTEGRATION WINSOCK_IPX ENGLISH=1)`, matching the original build exactly.

## Root-cause fix #4: `TRUE_FALSE_DEFINED` bool-polyfill guard collision (22 headers)
Same disease as `WWSTD.H` in 1a, independently reinvented in `CODE/`: 22 headers (`BAR.H`, `BENCH.H`, `BLOWFISH.H`, `BUFF.H`, `CRATE.H`, `CRC.H`, `FIXED.H`, `FTIMER.H`, `FUNCTION.H`, `KEY.H`, `KEYBOARD.H`, `LISTNODE.H`, `MIXFILE.H`, `MONOC.H`, `MP.H`, `PIPE.H`, `RECT.H`, `SEARCH.H`, `SHA.H`, `STRAW.H`, `WATCOM.H`, `WWFILE.H`) each carry an identical `#ifndef __BORLANDC__ / enum {false=0,true=1}; typedef int bool;` block that collides with the real C++ `bool`/`true`/`false` keywords. **Fixed** with a single `perl -0777` multi-line regex applied to all 22 files at once, changing the guard to `#if !defined(__BORLANDC__) && !defined(_MSC_VER) && !defined(__cplusplus)`; one further bare (unguarded) copy in `PACKET.CPP` was fixed by hand.

## Root-cause fix #5: `DDE.H`/`DDE.CPP` (Instance_Class) — three distinct bugs stacked
1. Missing `#include <ddeml.h>` — modern `<windows.h>` no longer pulls in DDEML types (`HSZ`, `HCONV`, `HDDEDATA`) implicitly the way the Win16-era SDK did.
2. Calling-convention placed outside the parens on two function-pointer-typed members (`BOOL CALLBACK (*)(...)` instead of `BOOL (CALLBACK *)(...)`) — same class of bug as `IPX95.H`'s ten `typedef ... __stdcall (*Name)(...)` declarations (also fixed, see below) and `PALETTE.H`... er, `WIN32LIB`'s own `SOUNDIO.H`-family bugs from 1a.
3. `dde_callback`'s last two parameters were `DWORD` where `ddeml.h`'s real `PFNCALLBACK`/`FNCALLBACK` typedefs require `ULONG_PTR` (pointer-sized on x64) — the same Win64 widening-drift bug class as 1a's `timeSetEvent` fixes.

## Root-cause fix #6: Greenleaf Communications Library (GCL) — confirmed proprietary and absent
`FUNCTION.H` unconditionally included `<modem.h>`/`<fast.h>` (GCL's raw serial-port API), and `NULLCONN.H`/`NULLMGR.H` unconditionally included `commlib.h` (GCL's `PORT` type) even in their `#else //WIN32` branches. None of these headers, nor the `gcl510/` directory the original `MAKEFILE` pointed `/i=` at, exist anywhere in this GPL release — genuinely proprietary and never redistributed. Confirmed `WIN32LIB/WINCOMM/WINCOMM.CPP` already reimplements every GCL function natively against the real Win32 serial API (its own comments literally say "Replacement for Greenleaf function: X"), so the Win32 build never needed GCL at all. **Fixed** by guarding all three includes to `#if !defined(WIN32) && !defined(_WIN32)`, and changing `NullModemClass::Abort_Modem`'s unused `PORT*` parameter to `void*` (every caller already casts it to a no-argument function pointer, so the parameter's type was never load-bearing).

## Genuine source-drop gaps found (confirmed absent, not fixed)
Consistent with 1a's `CCFILE.H`/`PALETTE.OBJ`(partially)/`PASSEDIT.OBJ` findings — checked the whole repo, not just `CODE/`, before concluding a header is genuinely missing rather than misnamed:
- **`phone.h`** (`PhoneEntryClass`/`PhoneListClass`, the null-modem dialer's phone-book) — blocked `NULLDLG.CPP` entirely and a self-contained ~140-line block inside `SESSION.CPP::Read_MultiPlayer_Settings`/`Write_MultiPlayer_Settings`. `NULLDLG.CPP` excluded from the build; the phone-book read/write block inside `SESSION.CPP` (which is otherwise very much alive — `SessionClass` is core multiplayer state) was excised in place, leaving the rest of those two functions intact.
- **GCL** (see above) — additionally, `NULLMGR.CPP`'s actual method *bodies* (not just its header) call GCL functions directly in many places regardless of the `#ifdef WIN32` split (`COM1`-`COM5`, `ASSUCCESS`/`ASUSERABORT`, `HMWaitForOK`, `HMSetUpEchoRoutine`, `CD_SET`, ...) — unlike `NULLCONN.H`/`NULLMGR.H`, this file's Win32 code path was never actually finished being ported off GCL. Excluded entirely.
- **`PassEdit.h`** (`PassEditClass`) — the Westwood Online login dialog's password-masking edit control. Blocks `WOL_LOGN.CPP` throughout; excluded.
- **`PaletteClass`** (see below) — unlike the above, this one was **reconstructed** rather than excluded, because the blast radius (~50 files depend on it for core palette-fade rendering) was too large to treat as a fringe feature. Owner decision, made after an explicit blast-radius estimate.

## `PaletteClass` reconstruction
`RGB.H` only ever carried a forward declaration (`class PaletteClass;`) and a `friend class PaletteClass;` grant inside `RGBClass` — the real class body never survived into this GPL release. Initial exclusion of a handful of dependent files revealed the true scope: `GamePalette`, `BlackPalette`, `CCPalette`, `WhitePalette`, `ScorePalette`, `InGamePalette`, etc. are used with `.Set()`/`.Adjust()`/`.Partial_Adjust()`/`.Closest_Color()`/`operator[]` across roughly 50 files — a core, load-bearing part of the palette-fade rendering system, not a fringe feature. **Reconstructed from scratch** (`CODE/PALETTE.H`/`CODE/PALETTE.CPP`) purely by reading every call site's actual usage — the interface (256-entry `RGBClass` array, `COLOR_COUNT`, indexing, `Set()`/`Set(delay, callback)` wrapping `WIN32LIB`'s existing `Set_Palette`/`Fade_Palette_To`, `Adjust()`/`Partial_Adjust()` wrapping `RGBClass::Adjust()`, `Closest_Color()` wrapping `RGBClass::Difference()`, and implicit `unsigned char*`/`unsigned char const*` conversions for the handful of call sites that treat a palette as a raw buffer) was fully determined by what every caller needed, not guessed. This makes `CODE/` **compile and link** against `PaletteClass`; whether `WIN32LIB`'s underlying `Set_Palette_Range` (VGA-hardware-register I/O, meaningless on modern Windows) actually paints anything is a separate, already-known gap for the Phase 4 rendering rewrite.

## `NOINIT.H`: a new shared header, extracted rather than invented
`NoInitClass` (the "construct without touching any members" tag struct used by the save/load pointer-fixup system) was defined inline inside `FUNCTION.H`, but 63 files reference it and several low-level headers (`GADGET.H`, `LINK.H`, `JSHELL.H`) need it without being able to include `FUNCTION.H` (that would reintroduce root-cause fix #2's circularity). Moved the definition into a new `CODE/NOINIT.H` (guarded `NOINIT_H`, with the original `NOINITCLASS` macro preserved so `FUNCTION.H`'s own guard logic keeps working), and added the new header directly to every file that clang's diagnostics showed actually needed it.

## The `TriggerTypeClass` mystery — an MSVC-2026-preview quirk, not a source bug
Three instantiation-forcing declarations in `FUNCTION.H` (`extern CCPtr<TriggerTypeClass> y15;` and a `template class DynamicVectorClass<CCPtr<TriggerTypeClass> >;` pair) triggered a spurious `C3203`/`C2990` ("TriggerTypeClass: unspecialized class template") under MSVC 19.51 (VS 2026 preview) — even though `TriggerTypeClass` is an ordinary class, `CCPtr<TriggerTypeClass>` is used successfully as a real class member a few hundred lines earlier in the same file, and **clang-cl reports zero errors** for the identical code. Extensive isolation (elaborated-type-specifier syntax, moving the declarations, checking for a stray `template<class T>` prefix elsewhere in the same translation unit) found no textual cause. Since these three lines are pure compiler hints — the file's own comment says "there are no actual objects... ever created" — and `CCPtr<TriggerTypeClass>` is genuinely instantiated elsewhere for real (`TACTION.H`'s `TActionClass::Trigger`, `TRIGTYPE.H`'s `TriggerClass::Class`), they were simply removed with a comment explaining why, rather than chased further.

## Other real bugs found and fixed (each individually diagnosed, not guessed)
- **27 instances of a bogus `template<class T>` prefix** on `CCPtr<ConcreteType>::Heap`'s out-of-class static-member definitions in `GLOBALS.CPP` (should have no `template` keyword at all — `AircraftClass`, `AnimClass`, etc. are concrete types, not template parameters). Same root cause independently produced the `TriggerTypeClass` red herring investigated above, and directly caused ~30 real errors once fixed in one pass.
- **"redundant `static`/`const` on an out-of-class member definition"** (illegal, but tolerated by Watcom) — found and fixed in: `DDE.CPP` (`Instance_Class::id_inst` etc.), `SEARCH.H` (`IndexClass<T>::search_compfunc`), `CONNECT.CPP` (`ConnectionClass::Commands`), `MIXFILE.CPP` (`MixFileClass<T>::Offset`), `MISSION.CPP` (`MissionClass::Is_Recruitable_Mission`) — the last two are `static` member functions whose *declarations* correctly omit `const`/have no qualifier, but whose *definitions* added one, causing MSVC to treat them as unrelated overloads ("member function not found").
- **Missing return type (K&R implicit-int)**: `SessionClass::Save`/`Load` (×4 overloads), `WWKeyboardClass::Down`, `Rotate_Bitmap`, two `static ... _last_pos/_last_frame` locals in `RADAR.CPP`.
- **`virtual` repeated on an out-of-class function definition** (illegal syntax, only valid in the class body): `SliderClass::~SliderClass`, `TextLabelClass::Draw_Me`.
- **`bool` used as a multi-value counter**: `ScenarioInit` (declared `bool`, used with `ScenarioInit++`/`ScenarioInit--` as a reentrancy depth counter across 15 files — `bool--` has never been legal C++) and `SCENARIO.CPP`'s local `retval`/`BGMessageBox`'s return type (needs a real 3-way `int`, not `bool`) — both changed to `int`.
- **Missing `typename`** on a dependent nested-type return (`IndexClass<T>::NodeElement`) in an out-of-class template member definition (`SEARCH.H`) — required by two-phase lookup, silently accepted by pre-standard compilers.
- **`fixed::operator*` ambiguity**: `unsigned short * fixed` (or the reverse) is ambiguous between the member `fixed::operator*(int)` (via `fixed`'s non-explicit `fixed(int)` converting constructor) and the friend `operator*(int, fixed const&)`, once the `unsigned short` operand promotes to `int`. Fixed with an explicit `(int)` cast at each of the ~10 call sites (all variants of `SomeClass->Class->MaxStrength * some_fixed_value`) rather than touching `fixed`'s fundamental (and widely-relied-upon) implicit-conversion design.
- **DOS-era APIs replaced with their modern equivalents**: `_dos_findfirst`/`_dos_findnext`/`struct find_t` → `_findfirst`/`_findnext`/`_findclose`/`struct _finddata_t` (`INIT.CPP`, `CDFILE.CPP`, `LOADDLG.CPP`); `_dos_getdrive`/`_dos_setdrive` → `_getdrive`/`_chdrive` (`STARTUP.CPP`); `_dos_getdiskfree`/`struct diskfree_t` → Win32's `GetDiskFreeSpace` (`CONQUER.CPP`, `SESSION.CPP`); `<i86.h>` (real-mode `union REGS`/`struct SREGS`) guarded to non-WIN32 only, since the code using it was already dead under WIN32 (`IPX.CPP`, `IPXMGR.CPP`, `NULLMGR.CPP`); `PATH_MAX` (POSIX) given a `#define PATH_MAX _MAX_PATH` compatibility shim where used (`CDFILE.CPP`, `STARTUP.CPP`).
- **Win64 API/type drift**: `HANDLE` used where `HINSTANCE` was meant (`hInstance` global, `Create_Main_Window`'s parameter, `Window_Dialog_Box`'s parameter — `HANDLE`/`HINSTANCE` are distinct `DECLARE_HANDLE` opaque types, not interchangeable); `Windows_Procedure`'s signature widened to the real `WNDPROC` shape (`LRESULT` return, `WPARAM`/`LPARAM` parameters) since it's directly assigned to `wndclass.lpfnWndProc`; ten `typedef ReturnType __stdcall (*Name)(...)` function-pointer typedefs in `IPX95.H` had the calling convention outside the parens (same bug class as `DDE.H`); `GetStockObject()`'s generic `HGDIOBJ` return needs an explicit cast to `HPALETTE`.
- **`mutable` needed on cache-invalidation flags mutated from `const` methods**: `ObjectClass::IsToDisplay` (cleared inside `Render() const`), `FootClass::IsScanLimited` (cleared inside `Greatest_Threat() const`) — same pattern as any lazily-updated cache field, the textbook use case for `mutable`.
- **`const char*`/`char*` propagation**: `strchr`/`strrchr`/`strstr` return the same const-ness as their input in C++ (unlike C); fixed by widening several local pointer variables to `char const*` where they're only ever read (`PROFILE.CPP`, `FIXED.CPP`, `WOLAPIOB.CPP`), and by an explicit `const_cast` in one place (`UDPADDR.CPP`) where the code genuinely mutates through a `char const*` returned by a `Get_Item() const` accessor — pre-existing, Watcom-tolerated behavior kept as-is rather than redesigned.
- **~130 instances of leaky pre-standard `for`-loop scoping** (Watcom let a `for (index = 0; ...)` reusing a variable persist into the enclosing block; standard C++ scopes it to the loop) — the large majority fixed by a purpose-built script (`fix_leaky_loops.py`) that parsed MSVC's `C2065` error list, matched each name back to its own `for (name = <literal>; ...)` line(s), and inserted the missing type — restricted to loops resetting to a literal constant, to avoid silently changing behavior for the rarer case where a loop's *final* value is read after the loop ends. That rarer "value must escape the loop" case (~15 instances, e.g. `LAYER.CPP::Sorted_Add`'s insertion-point search, `MAP.CPP`'s Tiberium-scan resume position, `SCORE.CPP`'s hall-of-fame slot search) was fixed by hand: hoisting a single `int`/`FacingType`/`CELL` declaration above the loop instead of declaring it in the `for`-init.
- **`Fancy_Text_Print`/`Simple_Text_Print`'s "dummy call to force font metrics" idiom**: ~20 call sites across the UI code repeat the exact idiom `Fancy_Text_Print(TXT_NONE, 0, 0, TBLACK, TBLACK, flags)` (draws nothing — `TXT_NONE` — purely to trigger internal font-loading side effects before a `String_Pixel_Width()` call). `TBLACK` (value 0) in the `fore` position — a `RemapControlType*` parameter — only ever worked because old compilers treated a zero-valued *named* enumerator as a null-pointer constant, which C++ has never actually allowed (only literal `0`/`nullptr` qualify). Fixed by replacing the `fore` argument with `NULL` at every occurrence of this exact idiom (verified the substitution didn't shift argument count via a careless first attempt — see below).
- **`Rect Shape_Dimensions`'s bottom/left/right edge scans** (`CONQUER.CPP`) reuse bare `x`/`y` across four separate edge-finding loops within the same function, needing `int x`/`int y` re-declared at each one (not a single hoist, since none of the four loops need the *previous* loop's final value — each resets its own start bound).
- **A real `MixFileClass<T>` template bug**: `class MixFileClass : public Node<MixFileClass>` (missing `<T>` on the base) — accepted by pre-standard/lenient compilers via the injected-class-name rule in some contexts, rejected by both MSVC and clang as a base-specifier here. Fixed to `Node<MixFileClass<T> >`.
- **A 64-bit pointer/enum type-punning trick** in `FactoryClass::Decode_Pointers` (`IOOBJ.CPP`) — `(HousesType)House` reinterprets an 8-byte `HouseClass*` as a 4-byte enum, which reinterpret_cast rules don't actually permit for pointer-to-smaller-integral conversions (this trick only ever worked because pointers and `HousesType` were both 4 bytes on 32-bit). Round-tripped through `intptr_t` to preserve the existing (already save-format-fragile-on-x64, flagged for later) truncating behavior rather than redesigning the pointer-fixup encoding here.
- **A missing overload declaration**: `WRITEPCX.CPP` defines `Write_PCX_File(FileClass&, GraphicBufferClass&, PaletteClass*)` but `FILEPCX.H` only declared the older `(char*, GraphicViewPortClass&, unsigned char*)` overload, so `CONQUER.CPP`'s call to the `FileClass&`-based version had nothing to resolve to. Added the missing declaration.
