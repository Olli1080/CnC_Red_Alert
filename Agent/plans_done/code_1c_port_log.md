# Sub-milestone 1c — Port Log (COMPLETE)

Parent plan: [../plans_wip/modernization_cmake_vcpkg.md](../plans_wip/modernization_cmake_vcpkg.md). **`redalert.exe` now links with 0 unresolved externals** and, when run against the owner's own legally-owned Red Alert CD1 data (via Steam's CnC Remastered Collection, which bundles the original classic assets), boots through DDE init, main-window creation, `REDALERT.INI` parsing, and MIX-file discovery, reaching real `IDirectDraw::SetDisplayMode` — verified with a from-scratch clean `cmake --build` and an actual run, not just a compile check.

## How to reproduce
```
cmake --preset Main
cmake --build build/Main --config Release --target redalert
```
`CODE/CMakeLists.txt` now has an `add_executable(redalert ...)` target linking `redalert_code` + `win32lib` + the system import libraries the original `MAKEFILE` would have linked implicitly (`ddraw`, `dsound`, `winmm`, `ws2_32`, `user32`, `gdi32`, `advapi32`, `shell32` — none of these are declared via `#pragma comment(lib,...)` anywhere in this tree, so they're listed explicitly).

## The three pre-1c architecture decisions (owner-approved before work began)
1. **ASM x64 mismatch → rewrite in C++ now.** Every remaining `.ASM` file (5 in `CODE/`, 61 in `WIN32LIB/`) is 32-bit-flat (`MODEL USE32 FLAT`), incompatible with this project's already-resolved x64-only target (x64 assembly has no `.MODEL`/segment/32-bit-calling-convention concept). Rather than mechanically port to x64 UASM syntax or reopen the x64 decision, Phase 5's already-planned "ASM → C++ rewrite" was pulled forward, scoped to just what 1c needs.
2. **Audio backend → keep DirectSound.** The main game audio path (`WIN32LIB/AUDIO/SOUNDIO.CPP`) already calls DirectSound directly, a real working Windows component — not the missing third-party SOS driver. The originally-planned miniaudio swap targeted the wrong layer; deferred to Phase 4's SDL3 migration.
3. **Movie playback → excluded for 1c.** VQA (`WINVQ/VQA32`) and MPEG movie playback both depend on the same never-shipped SOS driver (VQA) or a DLL that doesn't exist in this GPL release (MPEG); both stubbed/excluded with the same documented-exclusion discipline as 1b's `NULLDLG.CPP`, deferred to a future sub-milestone.

## Root-cause fix #1: old-compiler eager template instantiation (~239 of the original 374)
`FUNCTION.H` had a block of `extern CCPtr<ConcreteType> yN;` dummy declarations (`y1`-`y27`) whose only purpose was to force Watcom to instantiate `CCPtr<T>`'s members for 27 concrete types — Watcom (and Borland) instantiated *every* member of a class template as soon as *any* part of it was referenced, even via an inert `extern` declaration with no member call. MSVC/clang only instantiate members actually ODR-used in a visible translation unit. The same gap existed, with no forcing mechanism at all, for `VectorClass<T>`, `DynamicVectorClass<T>`, and `TFixedIHeapClass<T>`. **Fixed** by replacing the dummy-declaration idiom with genuine `template class X<T>;` explicit instantiation definitions, placed in the `.cpp` files where each template's out-of-line member bodies are actually visible: `CCPTR.CPP` (27 types), `VECTOR.CPP` (19), `DYNAVEC.CPP` (13 more, beyond 5 already-correct ones left in place in `FUNCTION.H`), `HEAP.CPP` (30 "Type Heap" classes). Also added `template class MixFileClass<CCFileClass>;` to `CCFILE.H` (same family, smaller gap — `CCFILE.H` already had the instantiation for a different concrete type, `CDFileClass`).

## Root-cause fix #2: bodyless declaration shadows a working template (~14 + 21 = 35 symbols)
`inline SomeEnum operator|(SomeEnum, SomeEnum);` (and `&`, `~`) — a plain declaration with **no body** — sits right after a working `template<class T> inline T operator|(T,T){...}` in `JSHELL.H`. Old compilers apparently treated the bodyless declaration as an instantiation request; standards-conforming compilers instead treat it as a **separate, never-defined non-template overload** that wins overload resolution (exact match beats template) and shadows the template, producing a link error. **Fixed** with genuine explicit-instantiation syntax (`template SomeEnum operator|(SomeEnum, SomeEnum);` — the `template` keyword, no `inline`) in `JSHELL.H`, `DEFINES.H`, `DRIVE.H`, `EDIT.H`, `GADGET.H` (bitwise `|`/`&`/`~`) and, once discovered during 1c's own work, the exact same pattern for postfix `operator++` on 21 more enum types in `DEFINES.H` (against a *different* pre-existing template, `template<class T> inline T operator++(T&,int)` in `JSHELL.H`, which had never been used this way before).

**A subtlety inside this fix**: `ABS`/`MIN`/`MAX` (`WWSTD.H`) and `Bound` (`JSHELL.H`) hit the identical bodyless-declaration symptom, but converting them to `template T FOO(T);` explicit instantiations broke a real call site (`WIN32LIB/IFF/LOADPCX.CPP:105`, `MIN(i - 1, height)` with mismatched `long`/`int` arguments) — template argument deduction requires every use of `T` to agree and rejects the call outright, where the original bodyless-overload behavior allowed it via implicit conversion. **Fixed** by writing these four as genuine non-template overloaded functions with real bodies per concrete type instead, restoring implicit-conversion-friendly overload resolution.

**A related, non-template case**: `Generate_Prime`, declared as a `friend` inside the `Int<PRECISION>` class template (needed for access to `Int`'s private nested `RemainderTable`), was a *different, non-template* friend function from the real `template<class T> T Generate_Prime(...)` defined just below the class — same shadowing symptom, different mechanism (friend injection instead of ordinary declaration). **Fixed** by forward-declaring the real template before the class and changing the friend declaration to `friend Int<PRECISION> Generate_Prime<Int<PRECISION> >(...)` (explicit-specialization-friend syntax), binding it to the one real template instead of silently declaring a second, empty entity. `Gcd`'s friend declaration has the identical bug but is never called anywhere in this codebase (confirmed via search) — left as-is with a comment rather than fixed, since there's no real generic `Gcd` template to bind it to and no call site to break.

## The ~66 `.ASM` files: rewritten as C++, not ported to x64 assembly
Per decision #1 above. Each file below got a fresh C++ implementation (not a literal instruction-by-instruction transcription) written from the ASM's documented behavior, its declaring header, and real call sites — matching the standard-algorithm-equivalent approach already established in earlier `WIN32LIB`/`CODE` work (e.g. Bresenham/Cohen-Sutherland line and rect clipping) rather than reproducing hand-tuned register tricks.

**Palette / blitting (`WIN32LIB/PALETTE`, `WIN32LIB/DRAWBUFF`)**: `PAL.CPP` (`Set_Palette_Range`/`Bump_Color`/`CurrentPalette`), `GETPIX.CPP`/`PUTPIX.CPP`/`CLEAR.CPP`/`FILLRECT.CPP`/`REMAP.CPP`/`DRAWLINE.CPP`/`TOBUFF.CPP`/`TOPAGE.CPP`/`BITBLIT.CPP` (standard blit primitives using the `Width+XAdd+Pitch` stride convention — `XAdd` is nonzero only for a plain in-memory buffer, `Pitch` only for a locked DirectDraw surface, so summing both unconditionally always yields the correct stride), `SCALE.CPP` (2x horizontal-interpolation image scaler, ported from the real `WINASM.ASM`/`WINVQ/VQAVIEW/INTERPAL.ASM` algorithm — a byte-shuffling trick decoded into a straightforward "each destination pixel pair is [source pixel, blend-toward-next]" loop against `PaletteInterpolationTable`), `STAMP.CPP` (combines `STAMP.ASM`'s tile/icon drawing and `STMPCACH.ASM`'s video-memory icon cache — `Clear_Icon_Pointers`/`Get_Icon_Index`/`Get_Free_Index` have no call sites anywhere in this release and weren't ported), `TXTPRNT.CPP` (bitmap font rendering + its `ColorXlat` 256-byte nibble-translation table — decoded the packed-nibble glyph format and the table's dual low-nibble/high-nibble-times-16 indexing scheme from first principles; the sibling `FONT/TEXTPRNT.ASM` is an older, unrelated `Text_Print` entry point over its own separate `ColorXlat`, matching the "duplicate implementation, only one really shipped" pattern already seen with `WWSTD.H`/`PROFILE.CPP` in earlier sub-milestones, and wasn't ported).

**Mouse cursor (`WIN32LIB/KEYBOARD/WWMOUSE.CPP`)**: `Mouse_Shadow_Buffer`/`Draw_Mouse`/`ASM_Set_Mouse_Cursor` — needed `friend` access to `WWMouseClass`'s private cursor fields (granted via a small header restructure in both copies of `MOUSE.H`, moving the `extern "C"` declarations above the class so the friend declarations can refer to the exact same entities rather than accidentally declaring new ones — the same "shadowing" risk as root-cause fix #2, avoided deliberately this time). `ASM_Set_Mouse_Cursor`'s compressed-shape path reuses `LCW_Uncompress` and the shared `_ShapeBuffer` staging buffer.

**Compression/animation (`CODE/LCWCOMP.CPP`, `WIN32LIB/WSA/XORDELTA.CPP`)**: `LCW_Comp` — a fresh LZ77-style encoder (single-candidate hash match finder) targeting the exact bitstream format `LCWUNCMP.CPP` already decodes, rather than a literal port of the original's exhaustive-search assembly; only needs to round-trip with this codebase's own decoder, not match the original encoder byte-for-byte. `Apply_XOR_Delta` (linear buffer) and `Apply_XOR_Delta_To_Page_Or_Viewport` (row/viewport-aware — the actual call site used by `WIN32LIB/WSA/WSA.CPP`'s WSA animation player, initially miscategorized as dead code before checking call sites more carefully) both decode the same Format80-style opcode stream (documented in the file's own commented-out reference implementation).

**Audio (`WIN32LIB/AUDIO/AUDUNCMP.CPP`)**: `Decompress_Frame` — the "Westwood ADPCM" codec used by every retail `.AUD` sound effect (`SCOMP_WESTWOOD`), fully decoded and ported (2-bit/4-bit delta tables, raw-copy and silence-run opcodes, saturating sample clamping). The separate "SOS" IMA-ADPCM-family codec (`SCOMP_SOS`, `SOSCODEC.ASM`/`OLSOSDEC.ASM`) was **not** ported — its real tables are two 89-row×16-token lookup tables (~180KB of precomputed constants) that would need error-prone hand-transcription with no way to verify correctness without real SOS-compressed test assets; `SOSCODEC.CPP` stubs `sosCODECDecompressData`/`General_sosCODECDecompressData` to silence (matching the block-size bookkeeping the caller does regardless of decode success) since `SCOMP_SOS` is a secondary/rare compression type per `SOUNDINT.H`'s own enum ordering, not what retail assets use.

**Misc small primitives**: `CPUID.CPP` (MSVC `__cpuid` intrinsic replacing the original's 386/486-detection dance — meaningless on x64, where CPUID/MMX have always been present), `WIN32LIB/MISC/{CLIPRECT,FADING,REVERSE}.CPP` + `WIN32LIB/MEM/{MEM_COPY,VMPAGEIN}.CPP` + `WIN32LIB/SHAPE/SHAPEBUF.CPP` + `WIN32LIB/PROFILE/APROFILE.CPP` (Westwood's own dev-only CPU sampling profiler — `Profile_Init`/`Profile_End`/`New_Profiler_Callback`, the Watcom `__PRO`/`__EPI` compiler-hook half of the original dropped since MSVC has no equivalent) + `WIN32LIB/DRAWBUFF/AUDIO`-adjacent `WINASM.CPP` (`Stop_Execution`, `Set_Palette_Register`, `ModeX_Blit` — a dead DOS/Win95 "Mode X" video path, no-op'd — and the `Asm_Interpolate*` scaler family).

**`CODE/2KEYFBUF.CPP` — `Buffer_Frame_To_Page`, the last unresolved symbol.** The original is ~3900 lines: a jump-table of per-effect-combination inner loops (normal/transparent/ghost/fading/predator, MMX and non-MMX, clipped and unclipped variants) plus a dual "new" (`ShapeHeaderType`-cache) / "old" (raw-buffer) source format switchable at runtime via `UseBigShapeBuffer`/`UseOldShapeDraw`. Rather than a full transcription, this port is scoped to exactly what this codebase's four call sites (all inside `CONQUER.CPP`'s `CC_Draw_Shape`, the aircraft/bullet "special shadow" rendering path) exercise: `SHAPE_TRANS` always on, combined with GHOST+FADING, FADING alone, PREDATOR alone, or GHOST-alone/neither. Source-buffer resolution reuses the already-correct, already-compiled `Get_Shape_Header_Data()` (from `2KEYFRAM.CPP`) rather than re-deriving its pointer arithmetic (which truncates a cache-base pointer to 32 bits elsewhere in this codebase — a pre-existing latent x64 issue, out of scope to fix here). The `GHOST` effect's `IsTranslucent`/`Translucent` table pair was decoded from `DisplayClass::SpecialGhost`'s actual construction (a same-color darken-toward-black shadow effect, not a true translucency blend, confirmed by every real caller using `SpecialGhost` specifically). The `PREDATOR` cloak-shimmer effect's Bresenham-style dither accumulator was ported faithfully; its obscure negative-offset table variant (reached via an address-arithmetic trick keyed off the sign of the caller's offset argument) was **not** replicated exactly — this port always cycles through the same small positive offset table regardless of sign, a safe approximation for a purely cosmetic effect, chosen over risking a wild pointer read from mis-replicating an under-documented trick.

## Dead-feature stubs (matching 1b's `NULLDLG.CPP` exclusion discipline)
- **`CODE/VQASTUB.CPP`**: `VQA_Alloc`/`VQA_Free`/`VQA_Init`/`VQA_Open`/`VQA_Close`/`VQA_Play`/`VQA_DefaultConfig`/`VQA_PauseAudio`/`VQA_ResumeAudio`. `WINVQ/VQA32/` already contains a full, real implementation of these, but it isn't wired into any CMake target and pulls in the same never-shipped SOS audio driver already excluded from the main audio path — wiring it in is future-sub-milestone work. `VQA_Alloc()` returning `NULL` is sufficient: both real call sites (`CONQUER.CPP`'s `Play_Movie`, `INTRO.CPP`'s `Open_Movie`) already treat a null handle as "movie unavailable" and skip playback gracefully (verified by reading both, not assumed).
- **MPEG movie playback**: `#define MPEGMOVIE` (unconditional whenever `DVD` is defined, in `DEFINES.H`) was commented out — it pulled in `MpgPlay`/`MpgPause`/`MpgResume`/`MpgSetCallback` from an MPEG-playback DLL that doesn't exist anywhere in this GPL release. One non-conditional call site (`MPGSET.CPP`'s settings-menu button handler) needed its own `#ifdef MPEGMOVIE` guard added, since it had implicitly relied on the macro always being defined whenever `DVD` was.
- **`CODE/NULLSTUB.CPP`**: `NullModemClass`'s missing methods (constructor/destructor/`Get_Message`/`Init_Send_Queue`/`Num_Send`/`Num_Receive`/`Send_Message`/`Service`/`Num_Connections`/`Response_Time`/`Reset_Response_Time`/`Set_Timing`/`Configure_Debug` — declared in `NULLMGR.H`, bodied only in the already-excluded `NULLMGR.CPP`) plus standalone functions themselves defined in the already-excluded `NULLDLG.CPP` (`Select_Serial_Dialog`, `Com_Scenario_Dialog`, `Com_Show_Scenario_Dialog`, `Find_Local_Scenario`) and modem lifecycle functions (`Modem_Signoff`, `Shutdown_Modem`, `Reconnect_Modem`, `Destroy_Null_Connection`, `WOL_Login_Dialog`). Every stub returns the same "cancelled/unavailable/nothing happened" sentinel its live caller already treats as the graceful non-multiplayer path — verified per call site. `NullModemClass` is instantiated as a real global (`GLOBALS.CPP`'s `NullModem`, "declaring this class doesn't perform any allocations" per its own comment), so the constructor/destructor specifically had to be safe to actually run, not just link.

## Genuine one-off bugs found and fixed
- **`bool`/`BOOL` global-variable linkage mismatches** (same disease across several files, each independently reintroducing it): `GameInFocus` (`GBUFFER.CPP`/`SOUNDIO.CPP`/`MOUSE.CPP` declared `extern BOOL`, `GLOBALS.CPP` defines `extern "C" bool`), `RA95AlreadyRunning` (`STARTUP.CPP` declared `extern bool`, `CCDDE.CPP` defines `extern "C" BOOL`), `GameTimerInUse` (`CCDDE.CPP` declared `extern BOOL`, `STATS.CPP` defines `bool`). MSVC's C++ name mangling encodes a global variable's type in its decorated name, so a mismatched `extern` links to a genuinely different symbol than the real definition — a link error, not just a correctness bug.
- **`RandNumb`**: declared `extern "C" { extern long RandNumb; }` in `INIT.CPP` but never defined anywhere in this GPL release — added the definition to `GLOBALS.CPP` (with matching `extern "C"` linkage — missed on the first attempt, which used plain C++ linkage and still failed to link for the same decorated-name-mismatch reason as the `bool`/`BOOL` bugs above).
- **`CPUType`/`VendorID`**: same genuine-gap pattern, resolved as part of the `CPUID.ASM` → `CPUID.CPP` rewrite (decision #1) rather than as a standalone fix.
- **Watcom `#pragma aux`** (inline-assembly function bodies MSVC/clang silently ignore, leaving a declared function with *no* body at all — a distinct root-cause category from missing `.ASM` files): `JSHELL.H` (`Set_Bit`/`Get_Bit`/`First_True_Bit`/`First_False_Bit`/`Cardinal_To_Fixed`/`Fixed_To_Cardinal`/`outportb`/`outport`), `RGB.H` (`outportb`/`outport`/`outrgb`, a duplicate declaration under the same guard), `COORD.CPP` (`calcx`/`calcy`, flagged as not yet verified bit-exact against real gameplay pathing/movement — needs real asset-driven testing to confirm). `outportb`/`outport` (raw VGA port I/O) are fundamentally impossible in Win32 usermode regardless of toolchain — confirmed dead/superseded by DirectDraw's palette API — and stubbed as no-ops rather than reconstructed.

## Runtime verification: two real bugs found by actually running the linked exe
Per the plan's own verification step, once `redalert.exe` linked, it was run against the owner's legally-owned Red Alert data (Steam's CnC Remastered Collection bundles the original classic `.MIX` files; hard-linked, not copied, into a scratch test directory alongside the built exe — see [../agent_policies/licensing.md](../agent_policies/licensing.md)). The first run hung indefinitely (no visible window, climbing CPU usage) rather than crashing — live-debugged with `cdb` (Windows SDK debugger) attached to the running process, which is what actually found these, not code inspection alone:

- **`RawFileClass::Open(int rights)`** (`CODE/RAWFILE.CPP`): its WIN32 branch's `if (Handle == NULL_HANDLE) { ...; return(false); }` had the `return(false)` (and the DOS-branch's `continue`) commented out, falling through to `break; return(true);` regardless of whether `CreateFile` actually succeeded — a genuine pre-existing bug in this GPL drop. Harmless under the *original* design, where the now-stubbed `Error()` was meant to show an interactive Retry/Abort dialog; with `Error()` correctly ported as a no-op (per the established "no interactive dialogs" pattern from earlier sub-milestones) and no return value change, a transient `CreateFile` failure silently became "success" with an invalid handle.
- **`RawFileClass::Read()`**'s own `while(size>0){ ReadFile(...); }` loop: on a `ReadFile` failure, called the (also no-op) `Error()` then `continue`d — retrying the identical failing read forever, since `size`/`bytesread` never change on failure. Same root cause as the `Open()` bug, different function.

Together, these turned a transient file-open hiccup (real-time antivirus briefly locking a rapidly-reopened file — `Bitdefender`'s hooks were visible in the process's loaded-module list during debugging) into a silent, permanent, CPU-burning hang with no error message and no visible window. **Fixed** by making both functions actually respect a failed Win32 call: `Open()` returns `false`, `Read()` breaks out of its loop and returns what was actually read — matching each function's own documented contract, and letting already-correct caller-side EOF/failure handling (`FileStraw::Get`, `Read_Line`) take over instead of spinning. Verified by rerunning under the debugger: the same file (`REDALERT.INI`) now reads and parses correctly, and startup proceeds past it to real `IDirectDraw::SetDisplayMode`.

## The DirectDraw 8-bit palette wall (confirmed platform limit, not a porting bug)
`Set_Video_Mode` (`WIN32LIB/MISC/DDRAW.CPP`) requests an 8-bit indexed-palette **exclusive fullscreen** mode via `IDirectDraw::SetDisplayMode(w, h, 8)`. This fails on any Windows Vista-or-later WDDM graphics driver — the OS no longer supports switching the physical display to 8bpp color at all, a well-known, universal limitation for classic DirectDraw 256-color games on modern Windows (not something fixable by further C++ changes; the driver itself refuses the mode). This is exactly the gap Phase 4's SDL3 + modern-renderer migration is scoped to close (replacing the raw 8-bit blit pipeline with a palette-emulating modern renderer). A third-party DirectDraw-to-Direct3D compatibility shim (dgVoodoo2) was considered as a today-only workaround to visually confirm rendering, but the download was flagged by the owner's antivirus and abandoned rather than investigated further or worked around — out of scope for this session regardless.
